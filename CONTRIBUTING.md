# Contributing

This project uses a **feature branching** workflow: `dev` is the shared integration branch, and all
work happens on short-lived branches that are merged back into it through a Pull Request (PR). This
keeps `dev` always releasable and every change reviewed before it lands.

- **`dev`** is the mainline. Branch from it, merge back into it. It should always be green (checks
  pass) and publishable.
- **`main`** is the protected, released state. It is updated from `dev` at release time, not by
  day-to-day feature work. Do not target it with feature PRs.
- **Never commit directly to `dev` or `main`.** Everything goes through a branch and a PR.

## The workflow, step by step

### 1. Start from an up-to-date `dev`

```bash
git checkout dev
git pull --ff-only origin dev
```

### 2. Create a feature branch

```bash
git checkout -b feat/short-description
```

Branch naming: `<type>/<short-description>`, lowercase, hyphen-separated. If the work maps to an
issue, include its number: `fix/42-cache-key-collision`.

| Type        | Use for                                 |
|-------------|-----------------------------------------|
| `feat/`     | a new feature or capability             |
| `fix/`      | a bug fix                               |
| `refactor/` | restructuring with no behavior change   |
| `docs/`     | documentation only                      |
| `chore/`    | tooling, deps, CI, housekeeping         |

Keep branches small and focused on one change. A branch that grows to touch several unrelated things
is a sign it should have been several branches.

### 3. Commit as you go

Make small, **self-contained** commits that each leave the tree in a **working state**. Use
[Conventional Commits](https://www.conventionalcommits.org):

```
<type>(<scope>): <imperative summary>

<optional body: what changed and why, not how>
```

Examples from this repo:

```
fix: correct cache identity, disposal, batching and object translation
refactor: rebuild FileLock on Semaphore and drop unreachable file helpers
ci: add dependency, static and secret scanning plus provenance publishing
```

Commit message rules:

- Summary in the imperative mood ("add", not "added"), around 50 characters, no trailing period.
- **Do not mix a refactor and a behavior change in one commit.** A refactor commit leaves the tests
  unchanged and green; a fix commit carries the test that proves the fix. Mixed diffs hide
  regressions and double the cost of review.
- Add a body only when the *why* is not visible in the diff — a non-obvious trade-off, a workaround
  for an upstream bug, a revert reason, a breaking change. Wrap body lines at ~72 characters.
- Commit messages must be **self-contained**. Describe the change itself, not the review process or
  any tooling used to produce it. Do not add co-author or "generated by" trailers.

### 4. Keep your branch current

While your branch is open, `dev` moves. Integrate regularly so the final PR merges cleanly and is
reviewed against current code. Rebase is preferred on a branch only you work on:

```bash
git fetch origin
git rebase origin/dev
```

If someone else is committing to the same branch, use `git merge origin/dev` instead, so you do not
rewrite shared history. Only force-push (`git push --force-with-lease`) branches that are yours alone.

### 5. Run the checks before you push

CI runs from a **fresh checkout**, so anything not committed does not exist there. Run the full gate
locally first, stopping at the first failure:

```bash
npm run format:check   # Prettier — CI fails on any formatting diff
npm run typecheck      # tsc over src/ AND tests/
npm run build          # tsc + tsc-alias into a cleaned dist/
npm test               # Vitest; e2e tests self-skip without DEEPL_API_KEY
npm audit --audit-level=high
```

New source and test files must be **committed**, not left untracked — they pass locally because the
file is on disk and fail in CI because it was never committed.

Add tests for new behavior. A bug fix should come with a test that fails before the fix and passes
after it. See [docs/conventions/testing.md](docs/conventions/testing.md).

### 6. Push and open a Pull Request

```bash
git push -u origin feat/short-description
```

Open the PR **into `dev`**. A good PR:

- Has a clear title (the Conventional Commit summary works well) and a description covering what
  changed, why, and how to verify it.
- Is small enough to review in one sitting. If it is large, say why, or split it.
- Links the relevant issue.
- Is green before you request review.

### 7. Review and merge

- At least one other person reviews and approves. Address feedback with follow-up commits on the same
  branch (or amend + `--force-with-lease` if the branch is yours alone).
- Re-request review after non-trivial changes.
- CodeRabbit reviews every PR into `dev` and `main` on its own; `@coderabbitai full review` as a
  comment re-runs it. Its findings are advisory and do not gate the merge — the human approval
  above still does. `.coderabbit.yaml` in the repo root is the configuration, including the
  per-path instructions that hand it this project's conventions.
- Once approved and green, merge into `dev`.
- **Delete the branch** after merge. Locally: `git branch -d <branch>`.

## Never commit a secret

The translation providers are paid APIs and this repo is public.

- Keys live in `.env.dev`, which is gitignored. `.env.example` documents the variable names and holds
  no values.
- Scratch `.http` request files and editor REST environments must use a `{{DEEPL_API_KEY}}`
  placeholder, never the literal key.
- CI runs gitleaks over the full history on every pull request and on every push to `main`, and
  a hit fails the build.
- If a key does get committed: **rotate it first**, then clean the history. Rotation is the fix;
  removing the commit is cleanup.

## Pre-push checklist

- [ ] Branch is up to date with `origin/dev`.
- [ ] `format:check`, `typecheck`, `build`, `test` and `audit` pass locally.
- [ ] New source and test files are committed, not left untracked.
- [ ] New behavior is covered by tests; a fix has a test that failed before it.
- [ ] Commits are small, imperative, Conventional-Commit style, and self-contained.
- [ ] Refactors and behavior changes are in separate commits.
- [ ] No API key, token or `.env` file in the diff.
- [ ] PR targets `dev`, has a clear description, and links its issue.

## Quick reference

| Do | Don't |
|----|-------|
| Branch from `dev` | Commit directly to `dev` or `main` |
| Keep branches small and single-purpose | Bundle unrelated changes in one branch |
| Rebase your own branch onto `dev` | Rebase or force-push a shared branch |
| Run the gate before pushing | Rely on CI to catch what you can catch locally |
| Separate refactor commits from fix commits | Hide a behavior change inside a cleanup |
| Import through the `@/` alias | Write deep relative import chains |
| Export only from `src/index.ts` | Make a utility public by accident |
| Delete branches after merge | Leave stale merged branches around |
